## 标准渠道模板（2026-10-23 确认）

- 新增“标准模板”：管理员只填根地址，系统默认生成 Chat / Messages / Responses 三种协议地址，不提供协议开关。Chat 和 Responses 的 Base URL 为根地址加 `/v1`，Messages 使用根地址；请求仍分别追加 `/chat/completions`、`/v1/messages`、`/responses`。上游不支持的协议由冒烟测试和请求反馈报错，未来另行评估协议桥接。
- 根地址只允许 scheme + host + 可选端口，支持 HTTP/HTTPS，移除首尾空白和末尾斜杠；不接受路径、查询或片段，避免重复版本路径。
- 根地址仅作为表单输入，保存时展开到现有三个 Base URL 字段，不新增数据库字段或迁移。保存、拉取模型、冒烟测试使用同一套展开结果；标准模板用 `/v1/models` 拉模型。
- 标准模板编辑时从 Messages 地址恢复根地址。切入标准模板时，仅当现有三项地址符合标准组合才自动提取；切出标准模板到自定义时保留展开后的地址。其他官方模板地址保持独立。

## 范围与方向（2026-10-18）

- **定位**：面向团队内部使用，并支持未来开源后的独立团队部署；各实例独立管理支付商户、订单和余额。
- **自研**：不 fork 现有项目。`references/` 下的仓库只作为设计参考，代码不继承。
- **协议**：MVP 支持三个入口 `/v1/messages`、`/v1/chat/completions`、`/v1/responses`。
- **System One（2026-10-22 确认，本地实现并验证）**：新增 `/v1/systemone` 原生 JSON 透传，接入 TypeSafe 与 Nace 两个渠道模板。渠道独立保存 System One 地址，不复用聊天协议字段。支持拉取 `{ "models": [{ "name": "…" }] }` 上游模型列表，冒烟测试发送 `state` 与 `questions`；正式请求沿用现有鉴权、模型映射、分组、路由重试、计费和日志。用量读取 `usage.input_tokens` / `output_tokens`，价格仍由管理员按官方价录入（两家当前输出免费），不做聊天协议转换。仅支持非流式调用，显式拒绝 `stream: true`。管理端只对 `typesafe` 和 `nace` 模板显示 System One 协议及地址项。实测及边界见 [System One 接入记录](research/systemone.md)。2026-10-23 已发布到 DMIT；模板和入口可用，实际渠道需另行配置。
- **只做透传**：入口协议必须和渠道支持的协议一致，不做跨协议转换。不支持的组合返回明确提示，告诉用户该用哪个入口。适配和转换放到以后。
- **原始内容留存**：请求和回复全量保留，以后存云盘。MVP 先不做。

## 计费（2026-10-18）

- **只算用户这一本账**：扣费 = 模型标价 × 分组倍率。上游实际成本是现实世界的账，灵枢不管；以后最多加点辅助工具。
- **价格挂在模型上**，和走哪个渠道无关。同一个模型不管路由到哪个渠道，用户付的钱一样。
- **价格规则（2026-10-21 实现，2026-10-23 更新）**：每个模型在基础价之外可以配置按顺序的规则（存在 `models.price_rules`，结构见 `internal/billing/rules.go`），第一条条件全部满足的生效，都不满足用基础价。条件：生效日期范围（北京时间，两头都含，用来提前配好厂商公布的涨价 / 降价 / 限时价）；总输入（输入 + 缓存命中 + 缓存写入，和 OpenAI、Anthropic 一致）**超过** N token（"≥ 200K" 填 199999）；北京时间每天的时间段（含开始不含结束，可跨零点，以请求开始时间为准，固定 UTC+8）；可选“仅周末”。周末固定为北京时间周六、周日。`days` 只接受空值或 `weekend`。每条规则直接填 4 个价格（不用倍数），同样乘分组倍率。结算时匹配；日志的单价列记实际生效价，`price_rule` 记规则名。上游成本也按规则价算。没填名称的规则按条件自动命名。成员在"模型与价格"页能展开看到规则价。
- **站内价 = 模型厂商官方按量计费价**（2026-10-21 用户重申）：卖给成员的价格只看厂商官方价，默认国际站美元价，和走哪个渠道、渠道花多少钱无关。渠道成本（中转价、充值手续费、中国站和国际站差价）是我们自己的账，用渠道余额估算的成本系数记。价格要以厂商官方价格页为准，OpenRouter 等转售渠道的标价只作参考。
- **价格维度**：MVP 每个模型按每百万 token 定 4 个价：输入、输出、缓存读、缓存写。图片、音频、联网搜索、长上下文阶梯价以后再加。
- **usage 统一口径**：计费前先把各协议的 usage 换算成统一口径。Anthropic 的 `input_tokens` 不含缓存部分，OpenAI 的 `prompt_tokens` 含 `cached_tokens`。
- **定价来源**：模型标价用厂商国际站的 USD 价格；没有国际站价时，用中国站价格按汇率换算。价格以 USD 存库，改汇率不影响已录入的价格。
  - DeepSeek 按北京时间分时计价：周一至周五 09:00–12:00、14:00–18:00 为高峰，其余时段及周末全天为低谷；低谷为高峰五折。按自然星期和时段匹配。
  - 阿里缓存按显式缓存算：写入 = 输入价 × 125%，命中 = 输入价 × 10%。
  - Kimi 缓存写入按 5 分钟档。
  - 限时免费、不单独收费的缓存写入，价格填 0。
  - 当前价格表见 `docs/research/upstream-protocols.md`，开发库由 `scripts/seed-dev.py` 写入。
- **货币**：账本统一用 USD，存成高精度定点数（如 `NUMERIC`），不用浮点数。汇率只用在显示人民币和充值换算上，每笔充值记下当时的汇率。
- **扣费流程**：请求进来时只检查余额是否大于 0，完成后一次性扣费，允许小额透支。MVP 不做预扣，数据结构上留出预扣的位置。key 的限额用同一套逻辑。

### 流式请求和失败场景的计费规则

规则不分协议，三个入口一致。依据见 `references/` 调研（new-api、sub2api、litellm、bifrost 的对比）。

| 场景 | 规则 |
|---|---|
| 用户中途断开 | 立刻取消上游请求，按已收到的内容扣费 |
| 上游中途出错或截断 | 不扣用户 |
| 流结束了但没有 usage | 用 tokenizer 估算，绝不按 0 算，记录标成"估算" |
| 失败重试 | 每个请求只结算一次，失败的尝试不收钱 |
| 什么时候允许重试 | 只在还没给客户端发出第一个字节之前 |

- `/chat/completions` 的流式请求：网关自动加上 `stream_options.include_usage: true`。客户端本来没要这个参数的话，把末尾那块 usage 数据截下来不转发。

## 角色、用户分组与服务分组（2026-10-23）

- 角色只控制管理后台权限（`admin` / `user`），不代表服务使用范围。
- 用户分组用于给用户归类，例如 `default`、`internal`；一个用户可加入多个用户分组，新用户自动加入 `default`。
- 原「分组」改称服务分组，继续承载价格倍率和渠道归属。服务分组增加启用状态与适用范围：所有用户，或指定的一个或多个用户分组。用户属于任一被指定的用户分组即可使用该服务分组。
- 用户创建 API Key 时只列出已启用且对其可用的服务分组；请求时再次检查可用范围和启用状态。停用服务分组会立即阻止新建和现有 Key 的后续请求。
- 用户分组管理放在用户管理页；服务分组管理继续放在定价页。界面使用“所有用户 / 指定用户分组”说明范围，避免将“公开”误解为无需登录或对互联网开放。
- 迁移时保留原有用户对特殊服务分组的访问结果；旧的直接授权转成用户分组成员资格和服务分组允许列表。

## 路由与重试（2026-10-18）

- 渠道按优先级分档，先用最高一档，这一档全部失败再往下一档走。兜底渠道就是最低的那一档。
- 429、5xx、超时、连不上：换渠道重试。401/403：换渠道重试，并把渠道标成异常。
- 400 请求错误、上下文超长、内容审核拒绝：不重试，原样返回。
- 同一档内多个渠道平均分流量，随机选。不设权重，以后真撞限额再加。
- 最多尝试 3 个渠道，总耗时有封顶。连续失败的渠道暂停几分钟后自动恢复。
- 带 `previous_response_id` 的请求必须发回原渠道，不能换渠道兜底（状态存在原上游账号里）。
- 渠道冒烟测试除了测通不通，还要实测流式响应里有没有带 usage。
- 各上游支持哪些协议，查证结果见 `docs/research/upstream-protocols.md`。

## 日志体系重构（2026-11-04 确认）

日志是整个项目的核心数据，先把记录做准、做全，统计图表以后另开页面，基于日志再做。

- 「全站日志」和「账户日志」各分为两个标签：**调用日志**（默认）和**操作日志**。不叫“运行日志”（易误解为服务进程日志），也不叫“审计日志”（对成员太重）。
- 原因：调用和资金变动回答的是不同问题，合在一张表里一半列对另一类恒为空，而默认视图看不到首字、耗时、缓存这些最常用的信息。
- 分两次发布：先调用日志，再操作日志。后者要改约 25 个写入接口，单独验收，避免一处出错整体回滚。

### 调用日志

- 列：时间、（用户）、Key、服务分组、模型、（渠道）、状态、Tokens、速度、花费；括号内仅管理员可见，成员照旧看不到渠道和上游模型名。
- Tokens 格主行“输入 / 输出”（输入含缓存），次行缓存命中率 = 缓存读 ÷（输入 + 缓存读 + 缓存写）。
- 速度格主行“首字 · 输出 tok/s”，次行总耗时。tok/s = 可见输出（输出 − 推理 token）÷（总耗时 − 首字时间）；非流式、首字后传输不足 1 秒或可见输出不足 50 时显示“—”，不硬算。成员也可见速度，判断“是不是网关慢”的首先是用户本人。
- 速度口径修正（2026-11-05 实测）：推理 token 在首字前的静默里生成，测不到时间，计入分子会虚高；咔咔-gpt0.18 有约六成流式请求把可见内容攒好后在 0.1 秒内一次发出（合成请求未能复现，原因未定），原口径算出数千至数万 tok/s。正常流式的可见速度中位数约 91 tok/s。
- 不做慢请求红黄绿着色：推理模型首字天然慢，拍脑袋的阈值会天天误报。
- 汇总卡片：花费、请求数（含失败数）、输入 / 输出 tokens、整体缓存命中率。
- 「模型」列升级为「请求」（2026-11-05）：主行模型名，次行「协议 · 流式/非流式 · 推理强度」。推理强度按客户端原样记录：chat 的 `reasoning_effort`、responses 的 `reasoning.effort`、messages 的 `output_config.effort`；messages 只传 `thinking` 时记 `budget:N` 或 thinking 类型。字段位置参照 new-api、sub2api 的解析。
- 访问者 IP（2026-11-05）：请求日志记 `client_ip`，管理员在用户名下方看到，成员在详情里看到自己的。取 IP 时，请求来自本机或私有网段（同机 Docker 网桥上的 Caddy）才信 `X-Real-IP`；原先只信回环地址，DMIT 的 Caddy 在 Docker 里，导致登录防护和日志拿到的都是 `172.18.0.4`，所有人共用一个 IP 计数。
- 日志表格比屏幕宽时在表格内左右滑动，页面本身不被撑宽。
- 首字列：非流式（首字≈总耗时）和失败请求显示“—”。流式首字是网关转发第一个事件的时间，含 `message_start` 这类空事件，略早于第一个 token。
- 耗时拆分（2026-11-06，参考其他网关的“读体 / 转发”）：日志另记读体（`read_ms`，接收客户端请求体用的时间）和发往上游的时刻（`upstream_start_ms`，有换渠道时按最后一次算），迁移 0026。首字改为从发给上游算起，和上游自身的响应速度对应，不再包含读体和网关处理；旧日志没有这两项，仍按旧口径显示。详情里拆成读体、网关处理（鉴权、选渠道、预扣、换渠道重试）、首字、转发（发给上游到传完）、总耗时。列表次行只在读体达到 0.5 秒时提示，多半是用户上行慢、上下文大。输出速度的算法不变。
- Key 名、渠道名自迁移 0003 起已在写入时快照；补上服务分组名快照。原因：分组删除后外键置空，历史日志看不出当时的分组（Relay-GPT 删除已实际发生）。迁移按现有关联回填。
- 调用日志保持与扣费同事务同步写入，不改异步批量：参考项目的异步队列都有“扣了费但日志丢失”的坑，本项目请求量（约每周 2–3 千）不需要用可靠性换吞吐。
- 本轮不做日志保留清理（量小）和原始请求 / 回复内容留存（独立需求，另行决策）。参考调研见 `docs/research/logging-references.md`。

### 操作日志

- 新表，一次状态变更一行：操作人（系统动作记“系统”）、受影响用户、动作、对象类型 / ID / 当时名称快照、字段改前 → 改后。
- 与业务改动在**同一数据库事务**写入：改成功必有记录，记录失败则改动一并回滚。
- 防漏记：测试枚举全部写路由，每个要么实际写操作日志，要么在显式豁免清单内，否则失败。新增接口忘记接入会被 `make test` 拦下。
- 每条记录挂「受影响用户」，管理员对某用户的操作该用户自己可见（避免 new-api 审计只归操作者、被操作者看不到的问题）。
- 密钥类字段（渠道 key、支付密钥、密码）只记“已更换”，不记值。
- 覆盖：用户、用户分组、服务分组、模型定价、渠道、Key、注册码、系统设置、支付配置、改密码、注册、充值到账、余额调整。不记：只读或试探性操作（拉取模型、冒烟测试、余额查询、支付探测、Pancake 目录与建商品）、未付款订单、个人偏好、登录登出（登录失败已在服务日志）、渠道拖拽排序（只影响列表显示，路由看优先级字段）。
- 变更内容由同一事务内改前 / 改后两份快照比对得出，不在各接口手写字段；快照里的关联数据用名称（如渠道所属分组、模型映射）。一个字段都没变的保存不记。新建记“改后”全部字段，删除记“改前”全部字段，便于事后知道删掉的是什么。
- Key 的名称 / 启停 / 分组与限额原是两条独立写入，可能只改一半；改为同一事务，一次修改一条记录。
- 余额调整和充值到账同时写入操作日志；`balance_adjustments` 仍是余额流水的权威来源，历史流水用迁移回填到操作日志。其他历史操作无从回填，从上线起记录。
- 成员只看与自己账号相关的记录（自己的 Key 增删改、改密码、充值、被调整余额、被启停），管理员专用字段（如用户备注）不出现。
- 筛选：时间、操作人 / 用户、对象类型。

## CI 与自动发布（2026-11-05 确认）

- 原因：本机 WSL → DMIT 上行变慢（5MB 成品 7–16 分钟，还断过），测试也依赖本机环境。改为 GitHub 上检查、构建，DMIT 自己拉取。
- 流程：检查 → 合并 → 自动发布 → 核实。暂不做云端只读审查。
  1. **CI**：PR 和推送到 main 都跑 Go 全量测试（临时 PostgreSQL）、`go vet`、前端类型检查与构建、三个浏览器回归脚本。
  2. **合并**：功能在分支上开发、开 PR，CI 全绿后合并到 main；合并即“同意上线”。
  3. **发布**：main 上 CI 通过后，GitHub 构建成品，发布到滚动预发布 `main-latest`（成品、SHA-256、清单）。清单列出全部迁移文件，并标出会丢数据的破坏性迁移（判断规则见下）。
  4. **DMIT 拉取**：每分钟检查一次清单，发现新提交就下载、核对哈希、单独备份、保存旧版本、替换、健康检查；失败自动换回旧版本并记下这个提交，不再重试。GitHub 里不存 DMIT 的任何凭据；仓库公开，下载无需 token。不从 GitHub 推送，也是为了避开 DMIT SSH 的连接限流。
  5. **核实**：服务端由助手核对版本、哈希、迁移和日志；用户在浏览器里看。
- 自上次发布以来只改动 `docs/`、`*.md`、`.github/`、`deploy/`、`scripts/`、`LICENSE` 时不发布（`deploy/`、`scripts/` 于 2026-11-06 加入：前者是手动装到服务器上的脚本和配置，后者是本机脚本，都不进成品）：成品嵌入提交号，否则纯文档提交也会让 DMIT 重启一次、可能打断流式请求。
- 破坏性迁移不自动上线：待执行的迁移里有清单标出的破坏性迁移时，发布脚本暂停，等用户确认后手动发布（需要恢复备份才能回滚的变更必须有人确认）。
- 破坏性的判断（2026-11-06 修正）：去掉 SQL 注释后含删表、删列、`TRUNCATE`、`DELETE FROM` 的迁移算破坏性。删列在 Postgres 里可以不写 `COLUMN`，所以 `DROP` 按排除法判断：删约束、索引、默认值、`NOT NULL`、触发器、视图、函数不丢数据，不算。原先凡含 `DROP` 都算，0024 只删了一个 CHECK 约束也被暂停。`UPDATE` 不算：改值的迁移按单次评审处理。
- 发布前备份单独命名 `lingshu-deploy-<时间>-<提交>.dump`、单独保留最近 10 份，不占每日备份的 14 份名额。
- 手动发布流程保留作为备用。

## 模型检测（2026-11-06 确认方向，试验中）

- 目的：发现上游“掺水”。一种是换模型（便宜模型冒充、量化版），一种是模型没换但偷偷降配（降推理强度、截断上下文、压低输出上限）。
- 做法：一律和官方对照组比，不定绝对分数。官方样本用用户自己的官方账号（本机 Magpie 的 `codex/*`，走 Codex），对 gpt-6.1-sol、gpt-6-astra、gpt-6.1-terra、gpt-6-luna 各跑两轮，第二轮换个时间跑，用来量官方自己的波动。terra、luna 用来验证能不能分辨“同家族降级”。
- 界面：单独做「检测」页面，选渠道和模型发起检测，不放在渠道页，和路由、计费解耦。检测请求直接打到指定渠道，不走路由，花费单独记账，不进调用日志和连接状态。
- 检测题写成带版本号的数据文件 `scripts/probe/suite.json`，本机脚本和以后的检测页面共用。已有版本只追加、不修改，不同版本的结果不能互相比。脚本 `scripts/probe/probe.py`，官方样本存 `scripts/probe/baselines/`。
- 第一批检测项：
  - 分词指纹：同一条消息加不加探针文本，输入 token 的差值只取决于分词器，不受各家注入的系统提示词影响。能区分模型家族，同家族分不开。注入提示词的长度（“基准值”）随型号不同，可作为辅助证据。
  - 单词指纹：24 个“随机说一个……”的问题，每题 6 次，不推理（`reasoning_effort: none`），按答案分布算距离。单个“1–100 随机数”问题在 GPT-6 家族里答案几乎一样（都偏爱 47），必须用多个问题。
  - 数学题：按种子生成、本地算标准答案，分中档和难档；记正确率和推理 token 数，用来看思考深度和稳定性。
  - 大海捞针：约 10 万 token 的上下文里藏三个编号，看有没有被截断。
  - 鹈鹕：原样使用用户的提示词，生成后截图，交给官方看图模型按结构检查表逐项判定（车轮、车架、坐姿、肢体、可辨认、无悬空零件），HTML 留着给人直接看动画。结构检查表只抓粗糙错误（零件断开、腿从嘴里长出来），官方四个型号基本全过。
  - 鹈鹕的腿（`scripts/probe/legs.js`）：在无头浏览器里把动画拨到不同时刻采样，算每条腿各节长度、脚和踏板的距离、脚绕圈的方向和车轮转向。问题分三类：伸缩（任一节长度变化超过 12%）、没踩板（脚到踏板距离变化超过 12 像素）、反着踏（脚绕圈方向和车轮相反）；都没有才算“真实蹬踏”。满血的写法是固定大腿、小腿长度，由踏板位置反推膝盖（逆运动学）。
- 第一批结果（2026-11-06，官方 `codex/*`，推理强度 medium）：
  - 单词指纹：同一型号两轮之间的距离 0.20–0.30（sol 0.21、astra 0.20、terra 0.26、luna 0.30），这是官方自身的波动。sol 和 astra 之间 0.19–0.31，分不开；sol、astra 和 terra 0.46–0.50、和 luna 0.51–0.54，terra 和 luna 之间 0.56–0.59。不同档位之间最小 0.46，大于自身波动最大的 0.30，可疑阈值定 0.40。整个家族共有的“口头禅”（1–10 都说 7、水果都说 mango）分不出型号，靠 24 个问题的偏好叠加才分得出。
  - 数学题：最难的递推题 sol、astra 两轮 4/4，terra、luna 两轮 0/4，单这一题就能抓出换成小模型；luna 在其他难题上也时对时错。
  - 鹈鹕输出长度：sol、astra 约 4250–5000 token，terra、luna 约 2500。
  - 鹈鹕的腿：medium 下官方 10 份没有一份真实蹬踏（sol 多是伸缩，astra 伸缩加没踩板，terra、luna 脚不跟踏板）。用户在 Agent 工具里生成的那份 astra 是真实蹬踏。推测和推理强度有关，待用 high / xhigh 验证；成立的话，鹈鹕改用高推理强度考，中转降推理强度就会露馅。
  - 中转 咔咔 的 gpt-6.1-sol 和 gpt-6-astra：分词同家族，推理 token 接近官方，9 万 token 捞针 3/3，鹈鹕结构和官方一个水准，未见掺水；注入的提示词比官方多几十 token。
- 题库扩充（2026-11-06，检测题第 2 版）：单词指纹从 24 题扩到 195 题（新增 151 道英文、20 道中文，前 24 题原样保留；答案改按题目文本记录）。四个型号各跑了一轮新题（astra 在额度恢复后补跑）。各型号每道题的答案分布汇总在 `scripts/probe/baselines/fingerprint-distributions.json`（`probe.py dist` 生成）。

## GPT Fast 计费（2026-11-06 确认）

- 起因：Codex 的 `/fast` 等客户端会在请求里写 `service_tier: "priority"`（2026-07 起也可写 `fast`，是同一个档位）。网关原样转发，上游按 Fast 价收费，我们却按标准价扣用户的钱，每个 Fast 请求约亏一半。
- 只针对 GPT（用户决定）：只看 OpenAI 协议（chat / responses）的 `service_tier`；messages 协议里同名字段是 Anthropic 的另一套含义，不碰。
- 按模型开放：模型定价加「Fast 倍率」（`models.fast_multiplier`，迁移 0025），留空表示不开放。不开放时，网关转发前去掉请求里的 Fast 档位，按标准处理和计费，日志记“模型未开放 Fast，已按标准处理”。Ultrafast（6 倍）不开放，一律去掉。`auto`、`default`、`flex` 原样转发，按标准计费。
- 计价：先按价格规则选出单价（长上下文“输入超过 272K”照常生效），再乘 Fast 倍率，然后乘分组倍率。OpenAI 官方价（2026-11-06 核对）对 GPT-6 / 6.1 / 5.6 全系的 Fast 都是标准价 × 2，短上下文、长上下文都一样，所以一个倍率就能对齐，不用另配规则。日志的单价列记 Fast 后的实际单价。
- 以响应里的实际档位为准：上游流量突增时会把 Fast 请求降回标准并按标准价收费，响应写 `service_tier: "default"`，这时按标准价扣（日志记“Fast 被上游降为标准”）；响应没写档位（有的中转会去掉）按请求的档位算。没要 Fast 的请求不会因为响应写了 `priority` 而加价。
- 预扣：Fast 请求的冻结额同样乘倍率（在“最近 20 次最贵 × 2”封顶之后乘）。
- 渠道是第三方中转或号池时，上游可能不认 Fast，也可能按自己的价格收费。倍率挂在模型上，由管理员按成本决定开不开。
- 展示：成员的「模型与价格」页在模型旁标 `Fast ×2`，展开能看到 Fast 价，包括长上下文的 Fast 价；调用日志的「请求」列标 Fast，详情里有“速度档位”。

## 汇率统一与实时汇率（2026-11-06 确认）

- 系统只有一个汇率（人民币 / 美元），同时用于：用户看到的人民币金额、管理员用人民币录价格和调余额的换算、**收人民币的支付服务的充值单价**。原先 EPay 单价单独配置，与显示汇率可能不一致（用户付 ¥6.70 充 $1，页面却按别的汇率显示），改为跟随系统汇率；收美元的服务不受影响。下单时按当时汇率报价并锁定在订单里，之后汇率变化不影响已下的单。
- 汇率模式二选一：手动（管理员填）或实时（自动跟随市场）。实时数据来自 Frankfurter（`api.frankfurter.dev`，多国央行数据综合，免费、无需 key、无配额、不要求署名，开源可自托管）；ExchangeRate-API 免费接口要求在用到汇率的页面署名且禁止转发，不选。数据每天更新，每小时拉取一次；拉取失败沿用上次的值；单次变动超过 10% 视为异常不采用，等管理员确认。汇率保留 4 位小数。
- 汇率真正变化时记一条操作日志（操作人为系统）；拉取时间、来源、错误等状态不进操作日志，避免每小时一条。
- 已存的美元价格和余额不随汇率变；按人民币定价的上游模型（如混元）美元售价不会自动调整，需要管理员按需复核。

## 预扣费与调用限制（2026-11-06 确认）

- 原因：准入只看余额 > 0，并发长请求可以同时放行，结算后余额可被扣成大额负数；面向外部用户时就是实际损失。也没有任何并发和频率限制，单个用户可以占满上游额度、压垮服务（DMIT 服务内存上限 192MB）。
- **预扣**：放行前按“输入估算 + 最大输出 × 输出单价 × 分组倍率”冻结一笔额度（`users.reserved`），可用余额 = 余额 − 冻结；可用余额不够就拒绝（402），提示预估金额、可用金额以及“调低 max_tokens 或充值”。结算时在同一事务里解冻并按实际用量扣费，多退少补。输出量取请求里的 `max_tokens` / `max_completion_tokens` / `max_output_tokens` 与系统设置的“预扣输出上限”（默认 8192）中较小者；请求没写时按上限。原因：Claude Code 等常写 3–6 万，实际回复多为几千，全额冻结会让余额不多的用户几乎无法并发。代价是单次回复超过上限时仍可能小额透支（有界，不同于原来的无界透支）；要严格不透支可调高上限或设为 0（完全按请求写的上限）。价格规则按估算的输入长度匹配。进程重启时清零所有冻结（单进程部署，进行中的请求已随进程结束）。
- **2026-11-06 上线当天修正**：线上实测公式估算严重偏高（`gpt-6.1-sol`、约 10 万上下文、99% 缓存命中的请求，实际 $0.014–0.029，预扣 $1.22），余额约 $1.2 的用户每个请求都被拒。三个原因叠加：按原始 JSON 请求体估输入高估约 2.7 倍；高估后越过 20 万长上下文档位按阶梯价翻倍；缓存命中按全价算。调整为：
  - 有历史时，预扣额取公式估算与“该用户该模型最近 20 次成功请求中最贵一次 × 2”的较小者；无历史时按公式。
  - 可用余额不够预估、但该用户没有其他请求在进行且余额为正时，放行这一个请求并冻结剩余全部可用余额（单个请求最多透支一次，同原行为）；并发请求仍会因可用余额已被冻结而被拒。
  - 代价：单次请求远超历史（如缓存全部失效）时可能小额透支，但不会再有多个并发请求一起扣穿余额。
- **并发与频率限制**：按用户计，系统设置里可调，填 0 表示不限。默认每个用户同时最多 10 个请求、每分钟最多 120 个请求。超限返回 429 和 `Retry-After`，按入口协议的错误格式，客户端会自动退避重试（余额不足仍用 402，避免客户端反复重试）。计数在进程内存里（单进程部署）。
- 被拒的请求照常记调用日志（状态“被拒绝”），不扣费。
