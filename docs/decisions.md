## 范围与方向（2026-10-18）

- **定位**：只给团队内部用。不考虑对外服务、许可证合规和真实支付。
- **自研**：不 fork 现有项目。`references/` 下的仓库只作为设计参考，代码不继承。
- **协议**：MVP 支持三个入口 `/v1/messages`、`/v1/chat/completions`、`/v1/responses`。
- **只做透传**：入口协议必须和渠道支持的协议一致，不做跨协议转换。不支持的组合返回明确提示，告诉用户该用哪个入口。适配和转换放到以后。
- **原始内容留存**：请求和回复全量保留，以后存云盘。MVP 先不做。

## 计费（2026-10-18）

- **只算用户这一本账**：扣费 = 模型标价 × 分组倍率。上游实际成本是现实世界的账，灵枢不管；以后最多加点辅助工具。
- **价格挂在模型上**，和走哪个渠道无关。同一个模型不管路由到哪个渠道，用户付的钱一样。
- **价格维度**：MVP 每个模型按每百万 token 定 4 个价：输入、输出、缓存读、缓存写。图片、音频、联网搜索、长上下文阶梯价以后再加。
- **usage 统一口径**：计费前先把各协议的 usage 换算成统一口径。Anthropic 的 `input_tokens` 不含缓存部分，OpenAI 的 `prompt_tokens` 含 `cached_tokens`。
- **定价来源**：模型标价用厂商国际站的 USD 价格；没有国际站价时，用中国站价格按汇率换算。价格以 USD 存库，改汇率不影响已录入的价格。
  - DeepSeek 统一按高峰价（灵枢没有分时段计价）。
  - 阿里缓存按显式缓存算：写入 = 输入价 × 125%，命中 = 输入价 × 10%。
  - Kimi 缓存写入按 5 分钟档。
  - 限时免费、不单独收费的缓存写入，价格填 0。
  - 当前价格表见 `docs/research/upstream-protocols.md`，开发库由 `scripts/seed-dev.py` 写入。
- **货币**：账本统一用 USD，存成高精度定点数（如 `NUMERIC`），不用浮点数。汇率只用在显示人民币和充值换算上，每笔充值记下当时的汇率。
- **扣费流程**：请求进来时只检查余额是否大于 0，完成后一次性扣费，允许小额透支。MVP 不做预扣，数据结构上留出预扣的位置。key 的限额用同一套逻辑。

### 流式请求和失败场景的计费规则

规则不分协议，三个入口一致。依据见 `references/` 调研（new-api、sub2api、litellm、bifrost 的对比）。

| 场景 | 规则 |
|---|---|
| 用户中途断开 | 立刻取消上游请求，按已收到的内容扣费 |
| 上游中途出错或截断 | 不扣用户 |
| 流结束了但没有 usage | 用 tokenizer 估算，绝不按 0 算，记录标成"估算" |
| 失败重试 | 每个请求只结算一次，失败的尝试不收钱 |
| 什么时候允许重试 | 只在还没给客户端发出第一个字节之前 |

- `/chat/completions` 的流式请求：网关自动加上 `stream_options.include_usage: true`。客户端本来没要这个参数的话，把末尾那块 usage 数据截下来不转发。

## 分组（2026-10-18）

- 公开分组所有用户都能用，特殊分组由管理员单独授权。
- 用户建 key 时，从自己能用的分组里选一个。
- 一个分组可以挂多个渠道，支持跨渠道重试，包括转到兜底渠道（细节见"讨论中"）。

## 模型名映射（2026-10-18）

- 系统里先有站内标准模型名（价格挂在这里），用户只看到、也只用这些名字。
- 管理员配置渠道时，手动填写"渠道模型名 → 站内标准名"的映射，做法参考 new-api。

## 路由与重试（2026-10-18）

- 渠道按优先级分档，先用最高一档，这一档全部失败再往下一档走。兜底渠道就是最低的那一档。
- 429、5xx、超时、连不上：换渠道重试。401/403：换渠道重试，并把渠道标成异常。
- 400 请求错误、上下文超长、内容审核拒绝：不重试，原样返回。
- 同一档内多个渠道平均分流量，随机选。不设权重，以后真撞限额再加。
- 最多尝试 3 个渠道，总耗时有封顶。连续失败的渠道暂停几分钟后自动恢复。
- 带 `previous_response_id` 的请求必须发回原渠道，不能换渠道兜底（状态存在原上游账号里）。
- 渠道冒烟测试除了测通不通，还要实测流式响应里有没有带 usage。
- 各上游支持哪些协议，查证结果见 `docs/research/upstream-protocols.md`。

- MVP 只做账号密码登录。注册码、飞书登录、邮箱绑定、人机验证以后再加。
- 安全加固往后放。
- 不做真实充值，由管理员直接设置成员余额。

## MVP 范围（2026-10-18）

**做**
- 网关：三个入口透传、key 鉴权、按优先级选渠道并重试、结算扣费、每次请求一条日志（用户、key、模型、渠道、token、金额、耗时、成败）。
- 管理端：用户（创建、设余额、授权特殊分组）；分组（名称、倍率、公开/特殊）；模型（标准名 + 4 个价格）；渠道（模板、地址、key、协议、优先级、所属分组、拉取模型、名称映射、冒烟测试）；全站日志。
- 用户端：登录、余额、可用分组及其模型和价格、key 管理（名称、分组、限额）、自己的日志。

**不做**：接入教程、统计图表（日志能筛选、能看汇总金额就够）、真实充值、注册、邮箱、人机验证、SSO、原始内容留存、跨协议转换、安全加固。

**MVP 上游**：只接中国厂商 —— DeepSeek、Kimi、GLM、Qwen、Xiaomi MiMo、StepFun。OpenAI、Anthropic 等美国上游以后用代理接入（腾讯云上有现成代理，以后再修通）。
- 模型（站内标准名 → 上游模型名）：`deepseek-v4.1-flash` → `deepseek-flash`；`GLM-5.3`；`mimo-v2.6-pro`；`kimi-k3`；`step-5-preview`；`qwen3.8-max`；`qwen3.8-flash`。没写箭头的，上游名和标准名相同。
- 协议：Qwen 走 `/v1/messages`（`https://dashscope.aliyuncs.com/apps/anthropic`）；DeepSeek 同时走 `/v1/chat/completions` 和 `/v1/responses`（同一个 `https://api.deepseek.com`）；其余 4 家走 `/v1/chat/completions`。三个入口 MVP 都做，`/responses` 用 DeepSeek 验收。各家地址和坑见 `docs/research/upstream-protocols.md`。
- 渠道按协议分别填地址（智谱三个协议的 base 不同）。
- 上游没有 `/models` 时（智谱、阿里），模型列表由管理员手填，或由渠道模板预置。
- 结算时 usage 每个字段取流里最后出现的值，不累加，也不信开头的值（StepFun 每块都带累计值；阿里 `message_start` 的 input 不准）。实测见 `docs/research/upstream-protocols.md`。
- coding plan 订阅 key 的使用条款风险，用户已经知道，由用户自己决定用不用，技术上不做限制。先把技术跑通；以后可能购买官方 team 席位。
- 鉴权同时接受 `x-api-key` 和 `Authorization: Bearer`；两个都带且不同时逐个尝试（Claude Code 会同时发）。
- 响应里的 `model` 字段不改回站内标准名，原样透传上游返回的值（改写要逐块处理，收益小）。
- 透传时保留客户端原始的 User-Agent（Kimi Code 等订阅渠道要求真实 UA）。

**验收**
1. Claude Code 走 `/v1/messages`、Codex 走 `/v1/responses`、脚本走 `/v1/chat/completions`，和直连同一个上游对比：流式、思考强度、工具调用、缓存命中一致，无协议报错，体感延迟无明显增加。
2. 抽查日志：usage × 单价 × 分组倍率 = 实际扣费。
3. 主渠道 key 填错时自动切到兜底渠道，用户无感。
4. Claude Code 里按 Esc 打断：按已生成部分扣费，上游请求被取消。

- `piqode.com` 的 ICP 备案由用户自己处理。

## 技术选型（2026-10-18）

用户不会自己读代码，语言按性能和资源占用选。

- 后端 Go：大量并发流式转发、内存占用低（服务器空闲内存约 0.9G）、单二进制部署；参考仓库多数是 Go。
- 数据库 PostgreSQL：复用服务器已有实例，单独建库和用户；金额用 `NUMERIC`。
- MVP 不用 Redis：单实例部署，渠道健康状态放内存。
- 前端 React + TypeScript + Vite，构建产物嵌入 Go 二进制，整个服务只有一个进程。
- 部署：本地 WSL 编译 → 上传二进制 → systemd 托管 → Nginx 反代 `lingshu.piqode.com`。服务器在上海腾讯云（MVP 上游都在中国，网关放中国合适）；DMIT 洛杉矶机器性能不够，不用。
