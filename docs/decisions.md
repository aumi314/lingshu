## 范围与方向（2026-10-18）

- **定位**：只给团队内部用。不考虑对外服务、许可证合规和真实支付。
- **自研**：不 fork 现有项目。`references/` 下的仓库只作为设计参考，代码不继承。
- **协议**：MVP 支持三个入口 `/v1/messages`、`/v1/chat/completions`、`/v1/responses`。
- **System One（2026-10-22 确认，本地实现并验证）**：新增 `/v1/systemone` 原生 JSON 透传，接入 TypeSafe 与 Nace 两个渠道模板。渠道独立保存 System One 地址，不复用聊天协议字段。支持拉取 `{ "models": [{ "name": "…" }] }` 上游模型列表，冒烟测试发送 `state` 与 `questions`；正式请求沿用现有鉴权、模型映射、分组、路由重试、计费和日志。用量读取 `usage.input_tokens` / `output_tokens`，价格仍由管理员按官方价录入（两家当前输出免费），不做聊天协议转换。仅支持非流式调用，显式拒绝 `stream: true`。实测及边界见 [System One 接入记录](research/systemone.md)。2026-10-23 已随统一版本发布到 UM580D 和 DMIT；模板和入口可用，实际渠道需另行配置。
- **只做透传**：入口协议必须和渠道支持的协议一致，不做跨协议转换。不支持的组合返回明确提示，告诉用户该用哪个入口。适配和转换放到以后。
- **原始内容留存**：请求和回复全量保留，以后存云盘。MVP 先不做。

## 计费（2026-10-18）

- **只算用户这一本账**：扣费 = 模型标价 × 分组倍率。上游实际成本是现实世界的账，灵枢不管；以后最多加点辅助工具。
- **价格挂在模型上**，和走哪个渠道无关。同一个模型不管路由到哪个渠道，用户付的钱一样。
- **价格规则（2026-10-21 实现，2026-10-23 移除节假日条件）**：每个模型在基础价之外可以配置按顺序的规则（存在 `models.price_rules`，结构见 `internal/billing/rules.go`），第一条条件全部满足的生效，都不满足用基础价。条件：生效日期范围（北京时间，两头都含，用来提前配好厂商公布的涨价 / 降价 / 限时价）；总输入（输入 + 缓存命中 + 缓存写入，和 OpenAI、Anthropic 一致）**超过** N token（"≥ 200K" 填 199999）；北京时间每天的时间段（含开始不含结束，可跨零点，以请求开始时间为准，固定 UTC+8）；可选“仅周末”。周末固定为北京时间周六、周日。没有法定节假日设置；假日按其自然星期和当天时段计价，调休周末仍按周末计。`days` 只接受空值或 `weekend`；迁移会把旧 `non_workday` 条件改为 `weekend` 并删除 `cn_holidays` 设置。每条规则直接填 4 个价格（不用倍数），同样乘分组倍率。结算时匹配；日志的单价列记实际生效价，`price_rule` 记规则名。上游成本也按规则价算。没填名称的规则按条件自动命名。成员在"模型与价格"页能展开看到规则价。
- **站内价 = 模型厂商官方按量计费价**（2026-10-21 用户重申）：卖给成员的价格只看厂商官方价，默认国际站美元价，和走哪个渠道、渠道花多少钱无关。渠道成本（中转价、充值手续费、中国站和国际站差价）是我们自己的账，用渠道余额估算的成本系数记。价格要以厂商官方价格页为准，OpenRouter 等转售渠道的标价只作参考。
- **价格维度**：MVP 每个模型按每百万 token 定 4 个价：输入、输出、缓存读、缓存写。图片、音频、联网搜索、长上下文阶梯价以后再加。
- **usage 统一口径**：计费前先把各协议的 usage 换算成统一口径。Anthropic 的 `input_tokens` 不含缓存部分，OpenAI 的 `prompt_tokens` 含 `cached_tokens`。
- **定价来源**：模型标价用厂商国际站的 USD 价格；没有国际站价时，用中国站价格按汇率换算。价格以 USD 存库，改汇率不影响已录入的价格。
  - DeepSeek 统一按高峰价（灵枢没有分时段计价）。
  - 阿里缓存按显式缓存算：写入 = 输入价 × 125%，命中 = 输入价 × 10%。
  - Kimi 缓存写入按 5 分钟档。
  - 限时免费、不单独收费的缓存写入，价格填 0。
  - 当前价格表见 `docs/research/upstream-protocols.md`，开发库由 `scripts/seed-dev.py` 写入。
- **货币**：账本统一用 USD，存成高精度定点数（如 `NUMERIC`），不用浮点数。汇率只用在显示人民币和充值换算上，每笔充值记下当时的汇率。
- **扣费流程**：请求进来时只检查余额是否大于 0，完成后一次性扣费，允许小额透支。MVP 不做预扣，数据结构上留出预扣的位置。key 的限额用同一套逻辑。

### 流式请求和失败场景的计费规则

规则不分协议，三个入口一致。依据见 `references/` 调研（new-api、sub2api、litellm、bifrost 的对比）。

| 场景 | 规则 |
|---|---|
| 用户中途断开 | 立刻取消上游请求，按已收到的内容扣费 |
| 上游中途出错或截断 | 不扣用户 |
| 流结束了但没有 usage | 用 tokenizer 估算，绝不按 0 算，记录标成"估算" |
| 失败重试 | 每个请求只结算一次，失败的尝试不收钱 |
| 什么时候允许重试 | 只在还没给客户端发出第一个字节之前 |

- `/chat/completions` 的流式请求：网关自动加上 `stream_options.include_usage: true`。客户端本来没要这个参数的话，把末尾那块 usage 数据截下来不转发。

## 分组（2026-10-18）

- 公开分组所有用户都能用，特殊分组由管理员单独授权。
- 用户建 key 时，从自己能用的分组里选一个。
- 一个分组可以挂多个渠道，支持跨渠道重试，包括转到兜底渠道（细节见"讨论中"）。

## 模型名映射（2026-10-18）

- 系统里先有站内标准模型名（价格挂在这里），用户只看到、也只用这些名字。
- 管理员配置渠道时，手动填写"渠道模型名 → 站内标准名"的映射，做法参考 new-api。

## 路由与重试（2026-10-18）

- 渠道按优先级分档，先用最高一档，这一档全部失败再往下一档走。兜底渠道就是最低的那一档。
- 429、5xx、超时、连不上：换渠道重试。401/403：换渠道重试，并把渠道标成异常。
- 400 请求错误、上下文超长、内容审核拒绝：不重试，原样返回。
- 同一档内多个渠道平均分流量，随机选。不设权重，以后真撞限额再加。
- 最多尝试 3 个渠道，总耗时有封顶。连续失败的渠道暂停几分钟后自动恢复。
- 带 `previous_response_id` 的请求必须发回原渠道，不能换渠道兜底（状态存在原上游账号里）。
- 渠道冒烟测试除了测通不通，还要实测流式响应里有没有带 usage。
- 各上游支持哪些协议，查证结果见 `docs/research/upstream-protocols.md`。

## 登录防护（2026-10-19）

用户提出加自己维护的人机验证。结论：验证码只是补充，主防线是频率限制加锁定。

- 同一用户名（不分大小写）15 分钟内失败 2 次后要求人机验证，失败 5 次锁 15 分钟；同一 IP 放宽到 5 次 / 30 次（团队可能共用出口 IP）。锁定期间密码正确也进不去，返回 429。解锁后仍要验证。
- 人机验证用工作量证明（和开源 ALTCHA 同原理）：服务端发带签名的题，浏览器后台算约 0.2–2 秒，用户不用点图、不用输字符；每道题 5 分钟内有效且只能用一次。不接 reCAPTCHA / Turnstile（中国访问不稳定，也不想依赖外部服务）。只在失败之后出现，正常登录无感。
- 防护状态只存内存，服务重启清零；单实例部署可以接受。
- 已知取舍：别人可以故意输错让某个账号被锁 15 分钟。小团队可接受，以后有需要再改成"锁定后带验证仍可登录"。
- 新设置的密码至少 12 位（已有密码不受影响）。用户不存在时也比对一次密码哈希，响应时间一致，猜不出哪些用户名存在。
- 登录失败和被锁定写进服务日志（用户名、IP），见 `docs/deploy.md`。

## 上游账户（2026-10-19）

用户提出估算各厂商账号余额，作为运维工具，和站内金额完全隔离。

- 余额记在"上游账户"上（你在厂商那里的账号）。2026-10-20 改为**并入渠道页**：一个渠道一把 key，对应唯一一个账户（同一账号开两把 key 没有意义，限流和余额都按账号算）。渠道列表有"余额"列，点开是余额面板（充值、校准、流水、设置）；删除渠道时余额估算和流水一起删。以后一个渠道支持多把 key 时，每把 key 各对应一个账户。
- 站内统一美元（用户决定）：录入和显示按当前用户的货币偏好换算，库里存 USD；充值、校准流水另存输入时的原始金额和币种。改系统汇率会让人民币账户显示的余额跟着变，下次校准纠正。
- 上游成本 = 站内基础价（不乘分组倍率）× 账户的成本系数，默认 1。以后有需要再加按模型单独设上游价。
- 上游成本按上游的计费方式记，和是否向用户收费无关：上游中途断流、没给 usage 但已经开始输出时，按估算算成本（用户不扣）。成本记在 `request_logs.upstream_cost`，同时扣账户估算余额。
- 校准：把估算余额改成真实余额，差额记为"偏差"，并显示距上次校准的估算花费。成本系数默认 1，也是调平系数：由人或 AI 看流水里的偏差手动调，不做自动建议（用户决定，别搞复杂）。
- 自动校准：DeepSeek（`/user/balance`，取 `total_balance`）、Kimi（`/v1/users/me/balance`，取 `available_balance`，含代金券）每小时用关联渠道的 key 查一次；`moonshot.cn` 记人民币，其他域名记美元。其他厂商只能手动校准。
- 提醒线目前只在页面标红；邮件等通知和"服务挂了提醒"一起做。
