# 模型检测实测记录

规则和口径见 `docs/decisions.md`「模型检测」。这里是得出那些规则的实验数据，按时间顺序保留。

## 官方样本第一批结果（2026-11-06）

- 单词指纹：同一型号两轮之间的距离 0.20–0.30（sol 0.21、astra 0.20、terra 0.26、luna 0.30），这是官方自身的波动。sol 和 astra 之间 0.19–0.31，分不开；sol、astra 和 terra 0.46–0.50、和 luna 0.51–0.54，terra 和 luna 之间 0.56–0.59。不同档位之间最小 0.46，大于自身波动最大的 0.30，可疑阈值定 0.40。整个家族共有的“口头禅”（1–10 都说 7、水果都说 mango）分不出型号，靠 24 个问题的偏好叠加才分得出。
- 数学题：最难的递推题 sol、astra 两轮 4/4，terra、luna 两轮 0/4，单这一题就能抓出换成小模型；luna 在其他难题上也时对时错。
- 鹈鹕输出长度：sol、astra 约 4250–5000 token，terra、luna 约 2500。
- 鹈鹕的腿：medium 下官方 10 份没有一份真实蹬踏（sol 多是伸缩，astra 伸缩加没踩板，terra、luna 脚不跟踏板）。用户在 Agent 工具里生成的那份 astra 是真实蹬踏。推测和推理强度有关，待用 high / xhigh 验证；成立的话，鹈鹕改用高推理强度考，中转降推理强度就会露馅。
- 中转 咔咔 的 gpt-6.1-sol 和 gpt-6-astra：分词同家族，推理 token 接近官方，9 万 token 捞针 3/3，鹈鹕结构和官方一个水准，未见掺水；注入的提示词比官方多几十 token。

## 题库扩充（检测题第 2 版，2026-11-06）

- 题库扩充（2026-11-06，检测题第 2 版）：单词指纹从 24 题扩到 195 题（新增 151 道英文、20 道中文，前 24 题原样保留；答案改按题目文本记录）。四个型号各跑了一轮新题（astra 在额度恢复后补跑）。各型号每道题的答案分布汇总在 `internal/probe/data/baselines/fingerprint-distributions.json`（`probe.py dist` 生成）。
- 每道题的区分作用 = 同样本量下型号之间的差距减去型号自身的波动（答案一分为二算）。高随机的题（随机颜色代码、编名字）型号之间差距大，但自身波动也大，作用并不高；真正有用的是“每个型号都很固执、但固执的答案不同”的题，例如四大名著人物（sol 总说林黛玉，terra、luna 说孙悟空）、女孩名字（sol 总说 clara，luna 总说 maya）。
- 四个型号齐全后：195 题里 80 道区分作用 ≥ 0.3，46 道 ≤ 0.05（全家族同一个答案，比如 1–10 都说 7、行星都说 neptune、表情符号都说 🦦，对分辨型号没用）。中文题自身波动更小，区分作用高于英文题。
- 171 道新题一分为二（3 个对 3 个）：自身波动 sol 0.22、astra 0.18、terra 0.27、luna 0.37；sol 和 astra 之间 0.23–0.27，与自身波动相当、分不开；sol、astra 和 terra 0.49–0.52，和 luna 0.58–0.60。
- 希腊字母、表情符号两道题第一次因答案清洗规则把非英文字符删光，已修正规则并补跑（只补跑部分题时合并进这一轮已有的答案）。
- 清洗规则修正前，sol、terra、luna 的新题里带重音、假名的答案被删掉了部分字符（如 Týr 记成 tr、日语单词丢了假名），和修正后才跑的 astra 比会虚高区分度（曾误以为“木漏れ日”是 astra 独有，其实全家族都这么答）。已对 15 道外语词、人名、食物、地名题补跑三个型号。
- 比对时去掉拉丁字母上的重音（týr / tyr、comté / comte、ł→l 视为同一答案），假名和汉字不动，原始答案照存。修正后 78 道题区分作用 ≥ 0.3，48 道 ≤ 0.05。
- 已知小问题：单复数（loafer / loafers）仍算不同答案，个别题区分作用偏高；单复数归一容易误伤（bus），暂不处理。

## sol 与 astra 的区分（2026-11-06）

- sol 与 astra 的区分（2026-11-06）：sol 是 astra 的量化版，大部分偏好相同，但有稳定的偏移。195 题合计，两者之间比自身波动只大 0.036，置换检验 p≈0.003，说明差别真实存在。从旧样本挑出 21 道区分作用较大的题，用官方账号各再问 10 次做验证（第 4 轮，单独存）：
- 单题区分在新数据上明显缩水（平均 0.36→0.17，21 道里 9 道仍 ≥ 0.2），说明挑题时有一部分是运气；
- 但 21 题合起来，从新数据每题随机抽 3 个答案、按和旧样本的距离判断，sol、astra 各 300 次全部认对，抽 5 个也一样；
- 稳定的题：英文名字（sol 说 clara、astra 说 oliver）、舞蹈（salsa / Lindy Hop）、神话生物（chimera / basilisk）、国际象棋（knight 和 bishop 各半 / bishop）、绳结（bowline / 8 字结）、哺乳动物（穿山甲 / 水豚）、蔬菜（胡萝卜 / 欧防风）。
- 检测里加“sol 还是 astra”子项：只在对照型号是 sol 或 astra 时跑这 21 题，每题 3 次。尚未在中转渠道上验证（注入的提示词可能让分布偏移），检测页面做好后先在 咔咔 上实测。

## 检测页面第一版上线后的实测与改进（2026-11-07）

- 咔咔 的 gpt-6.1-sol 两次检测结论相反：第一次单词指纹最像 luna（0.39，和 sol 0.80）、数学难题 2/4、基准输入 4391；复测像 sol（0.22）、4/4、基准 4227。两次基准不同，说明打到了不同上游：号池里有上游拿 luna 冒充 sol。第一次没报“上游混用”，因为一次检测只用一个会话编号，Codex 号池按会话路由，248 个请求全打到同一个上游。
- 改为一次检测用 4 个会话编号（`probe.Sessions`）：单词指纹每题的几次分到不同会话，每个会话把题池答一遍、单独排名；其他检测项轮流分配；会话 2–4 各补一次基准请求。某个会话明显更像别的型号（不是对照型号或同组相近型号，领先 ≥ 0.08）判不通过，总结论写“部分请求疑似不是 X：第 N 个会话最像 Y”；各会话基准输入 token 相差超过 50 或指纹结论不同，报“上游混用”。模拟（每题 1 个答案 × 40 题）四个型号 300 次全部认对；40 个随机种子下真 sol、真 astra 零误报，混入 luna、terra 零漏报。
- 对照组：OpenAI Platform 渠道（官方 API）的站内 gpt-6-luna 实际映射到上游 gpt-5.6-luna，检测给出“和各官方型号都不太像”，结论正确；映射已由用户改正。官方 API 环境基准请求只有 11 个输入 token（Codex 号池约 4200）。
- 工具调用在官方 API 上报 400：OpenAI 部分型号在 chat 接口上不允许工具调用带推理强度。工具调用题改为 `reasoning_effort: none`，上游不支持时去掉推理强度重试。
- 推理强度 low / high 的比较改为只作参考、不计分：官方校准（lattice_hard，各 3 次）sol 的 high / low 推理 token 比为 1.19、1.07、1.37，astra 为 1.41、1.21、1.00，按“high 不到 low 的 1.15 倍就算没生效”会误报官方。要判断推理强度被偷降，需要两档差距更大的题，另行研究。

## 参考 hvoy 的检测项（2026-11-07）

用灵枢自己的 key（id 36「模型测试」）让 hvoy 检测，在 DMIT 上抓 Caddy → 灵枢这一段的明文，只提取这把 key 的请求，原始抓包随即删除。共 8 次检测（gpt-6-astra、gpt-6.1-sol 各 4 次），每次 8 个请求。资料在 `references/probe-sites/`（原 `references/hvoy/`，不进 git），提取脚本 `extract.py`。

**hvoy 的 8 项和出题方式**

| 检测项 | 做法 | 每次是否变化 |
|---|---|---|
| 知识时效 | 5 道近期新闻题，`max_completion_tokens` 10240 | 从题库抽，8 次共见到 16 道不同的题 |
| 推理计算 | “N 个托盘每个 M 个……”四则运算，`reasoning_effort: high` | 数字随机 |
| 结构化输出 | json_schema 严格模式，原样返回随机 nonce | nonce 随机 |
| 推理预算（Juice） | responses 接口，让模型读出系统信息里的 “Juice” 值再做运算 | 校验串随机 |
| 指令层级 | 系统提示“只能回 vvv”，用户问 2+3 | **固定** |
| 分词 / 注入 | 用户消息只有一个字母 `a`，看输入 token | **固定** |
| 分词指纹 ×2 | 随机中文、多文字混排乱码，`max_completion_tokens` 16 | 内容随机 |

**观察**

- 两项是逐字固定的请求，中转很容易认出来专门放行；其余靠模板加随机数。这印证了我们自己的原则：题目要自建、随机抽。
- 知识题全部是 2025 年 4 月的事件，对 GPT-6 家族没有区分作用；而且题面给的格式示例就是答案（40 题里 29 题的回答和示例完全相同），测不出真实知识。我们的知识时效题不能带示例答案，时间要贴近各型号的知识截止期。
- 数学题是很简单的算术，配合 high 推理强度，看的是推理有没有真的发生，不是智力。
- **Juice**：官方 Codex（本机 Magpie `codex/*`）28 次全部拒答（astra 低 / 中 / 高 / 超高四档各 4 次，再按 hvoy 原样参数 astra、sol 各 high 6 次）。经灵枢转发的 8 次里，渠道 24「咔咔-gpt0.18」3 次全部回答 48，kinght、ai8 和官方一样拒答。所以“回答了 Juice”本身就说明上游不是官方 Codex 环境，可以作为一项检测；值和推理强度是否对应还没测到（官方拿不到数）。官方 API 环境（OpenAI Platform）是否拒答待验证。
- 同一次检测里咔咔的一个 high 推理强度请求推理 token 为 0（日志 4346），疑似推理强度被降。
- 输入 token 基准（一个字母 `a` 的请求）：kinght 约 4200–4500（和官方 Codex 相近），ai8 约 18200（多注入约 1.4 万 token），咔咔在 4400、5800、18200 三档之间变化，符合此前“号池混用多个上游”的结论。

## 鹈鹕与推理强度（2026-11-07）

用户在本机 Codex（Agent，目录约定“不运行验证”）用 gpt-6-astra、推理强度拉满，按检测题原版提示词生成一份，主观评价各方面正常；`legs.js` 测量为真实蹬踏（各节长度不变，脚到踏板距离变化 ≤ 2.2 像素）。

再按检测脚本的单次调用方式，官方 astra（本机 Magpie）xhigh 生成 3 份：结构评判 3 份全过；腿部 1 份真实蹬踏（推理 token 5523，三份里最多），2 份伸缩（各节长度变化 50–60%），但脚都踩在踏板上（距离变化 ≤ 8.5 像素）。medium 下官方 10 份没有一份真实蹬踏，且有“没踩板”。

结论：推理强度越高越可能蹬对，但 xhigh 单次也只有约三分之一，单份鹈鹕不能作为推理强度是否被降的判据。完整档里鹈鹕只展示结构评判和腿部测量，作参考、不计分；要量化得多份统计，xhigh 每份约 9–12k 输出 token、3–5 分钟，成本高。样本存 `references/pelican/`（不进 git）。

## ztest、cctest 抓包（2026-11-11）

用 key「检测抓取」让两家检测站测灵枢（都落到「超超 claude」「1、超超 gpt」），逐条说明在 `references/probe-sites/out/ztest-detail.md`、`cctest-detail.md`。

- ztest：GPT、Claude 同一套 14 题通用模板（连通、原样复述、数 1 到 N 看假流式、自报身份、JSON、逻辑小题、几千 token 的捞针、字符串操作、随机后缀的工具名、四则运算、PDF、只回某词、长串字母核对用量）。GPT 那轮 13/14 非流式且带 `temperature: 0`，真 Codex 不会这样，容易被中转认出；除一道算术题外推理 token 都是 0，测不出降推理。借鉴：工具名随机化（已做）、核对上游报的输入 token（抓虚报用量）、GPT Responses 响应里官方才有的字段。
- cctest：伪装几乎是真的 Claude Code（完整系统提示、全套工具、回放一段固定的真实会话含带签名 thinking）；测服务端工具 web_search、code_execution，图片验证码识别，`output_config.format`，以及“凭第一反应列 300 多个整数”的数字序列（三种说法各一次）。三轮对比：题型和回放会话固定，编号、PDF 文字、验证码、数字个数随机。测 GPT 只发 3 个数字序列请求，判超超 gpt“疑似被替换（像 gpt-5.5）”。
- 用官方 Codex 原样重放 cctest 的数字题：官方 sol / astra 开头 247，terra 217、43，luna 214、37；超超 gpt 一轮像 sol 家族（247, 18, 331）、一轮 47, 312, 86 四个官方型号都不像——超超 gpt 混了别的模型，和 cctest 的结论一致（我们的检测 64 和 ztest 都碰巧打到真 sol）。

## 数字序列指纹评估（2026-11-11，暂不接入检测）

suite.json 追加 `numbers`（自己的题面，count 每次 290–330 随机，max 355；GPT effort low，Claude 不开 thinking），`probe.py --only numbers` 采官方样本：GPT 四个型号各 6 次（Magpie codex/*），Opus、Sonnet 各 6 次（OpenRouter 锁 Anthropic，约 $0.5；第一次因 max_tokens 1024 被思考吃光而作废，改为 8192 重采）。

- 开头套路大量撞车：217, 43 在 sol、astra、terra、luna 都出现；247, 18 在 astra 和 Sonnet 都有；17, 284 在 Opus 和 luna 都有。换题面后官方 sol 多从 217 开头（cctest 题面下是 247）。只看开头会认错。
- 留一法、按整体分布比（数值分成 36 段）只认对 21/34，领先幅度中位数 0.004；偏爱的数、开头 20 个、相邻差值、尾数更差（7–14/34）。错误里 sol / astra 互认 5 次（同底子，预期内），也有 Opus→astra、terra→Opus 这类跨家族错误。
- 加采后（sol、astra 各 30，terra 24）重评：分清具体型号最好也只认对 54/100，领先幅度 0，样本加多不见好转；把 sol / astra 并成一组和 terra 比，单样本认对 75/84（全猜大模型也有 71%）。
- 结论：不接入检测。它只能粗分大小模型，这件事单词指纹做得更稳；分不清具体型号。cctest 认出 gpt-5.5 靠的是大样本库，不是方法更强。样本和评估脚本存 `references/probe-sites/numbers/`，Claude 不再加采。
